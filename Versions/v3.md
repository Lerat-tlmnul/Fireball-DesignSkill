# 🛠️ UI Design Engineering v3 — Changelog

## The Evolution

UI Design Engineering v3 is not a rewrite. It is a **surgical correction** of v3-beta.

v3-beta had solid content but suffered from packaging bugs and internal contradictions that prevented it from being production-ready. v3 fixes these defects without touching the underlying philosophy.

The fundamental rule change:

> **v3-beta:** "The system describes best practices."
> **v3:** "The system practices what it preaches — no rule stated is violated by the file that states it."

---

# 📄 Frontmatter & Triggering

## Before (v3-beta)
- `name:` and `description:` at file head, without `---` delimiters
- `description` written as marketing pitch ("definitive operating system", "token-cost aware")
- Skill name in title case with spaces (`UI Design Engineering v3-beta`)

## Now (v3)
- **Valid YAML frontmatter**, enclosed by `---` / `---`
- `description` rewritten as **factual triggering condition**: when to use it, when not to use it
- **Name in slug format** (`ui-design-engineering`), conforming to folder/skill naming convention

Without this fix, the file risked not being parsed as a skill at all — this was v3-beta's most critical bug.

---

# ⚖️ Internal Contradiction Resolution

The core work of v3: the anti-generic law (section 1.1) forbade defects that the system shipped with itself.

| Contradiction in v3-beta | Fix in v3 |
|---|---|
| 1.1 forbids "Inter 16px/24px as universal rhythm", but `--font-sans` defaults to `'Inter', 'Geist'` | Default stack neutralized to `system-ui`; Inter removed with explicit note referencing Phase 4 |
| Generic blue accent palette shipped as only token set, without warning | Section 8 renamed **"Starter Token Scaffold"** with disclaimer: these values are a technical starting point, not a brand identity — reusing them unchanged for a real brief violates 1.1 |
| Announced typographic scale (1.25, base 16) did not match actual `--text-*` values defined | Tokens recalculated to follow true 1.25 progression: `12/14/16/20/25/31/39/49/61/76px` |

# 🐛 Bug Fix

## Before (v3-beta)
```css
.btn-primary:active { transform: scale(0.98); background: var(--accent-active); }
```
`--accent-active` was **never defined** in `:root` — the "production-ready" component silently broke.

## Now (v3)
- `--accent-active` defined in both light **and** dark mode
- Added to **Phase 6 QA Gate**: "Every CSS custom property referenced in component code is actually defined in `:root`" — to prevent regression

---

# ✅ New Phase 6: QA Gate

## Before (v3-beta)
- Workflow ended at Phase 5 (Execution)
- No formal verification step before delivery — rigor relied entirely on model self-discipline

## Now (v3)
- **Phase 6 added**, mandatory before any delivery
- 10 binary checkpoints (calculated contrast, touch targets, no interactive `<div>`, GPU-only animations, all tokens defined, etc.)
- Framed as a blocking gate: on failure, fix before responding — do not describe as "next step"

# 📐 Spacing Grid

## Before (v3-beta)
- 8pt scale listed up to 128px in prose (3.1), but CSS tokens went to `--space-16: 160px` without 160 mentioned in the rule

## Now (v3)
- Prose and tokens aligned: documented 8pt scale explicitly goes up to **160px**

---

# 🎯 Phase 2: Clarification

## Before (v3-beta)
> "When ambiguous, ask clarifying questions before generating."

Absolute rule, no distinction by impact — risks blocking on minor ambiguities.

## Now (v3)
- Nuanced: clarifying question **only if the ambiguity materially changes design direction**
- Otherwise: assumed intent is stated explicitly in the response, work continues without interruption
