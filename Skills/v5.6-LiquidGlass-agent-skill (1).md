# UI Design Engineering v5.6 · Liquid Glass · Agent edition

**Team: 1 orchestrator, 10 coders, 5 testers, 5 reviewers.**
- The orchestrator does not write site files. It picks a direction, assigns files, runs attempts, scores them, and keeps the best one.
- Each coder writes exactly one file.
- Testers run technical checks and report numbers.
- Reviewers judge substance: slop, fit to brief, Liquid Glass nav, copy, responsiveness.

## 1. Branch and select (not a straight line)

The build is a search, not a single pass:

1. **Brief first.** If the brief is missing (no subject, no audience, no tone), stop and ask one question. Never build from nothing.
2. **Attempt (up to 3).** Each attempt uses a different direction from the list in the orchestrator. A direction is never reused until all are tried.
3. **Build.** The 10 coders write their files once, in parallel, from the direction card.
4. **Judge.** Gates run first (deterministic). Then testers and reviewers run in parallel and return findings.
5. **Repair (up to 2 per attempt).** Each finding goes to the coder that owns the file. The coder fixes only what the finding names. Re-judge after each repair.
6. **Score.** Gate failures weigh 2 points, judgment findings weigh 1. Lower is better.
7. **Stop early** if an attempt has zero findings. Otherwise keep the best-scoring attempt.
8. **Report.** `REPORT.md` lists every attempt, the selected attempt, and every open finding. Open findings are never hidden.

Why this beats a linear pass: a wrong direction costs one attempt, not the whole build. A weak attempt can still produce a usable site, and the best one is chosen on evidence.

## 2. Team

| Role | Count | Writes site files | Output |
|---|---|---|---|
| Orchestrator | 1 | no | Direction card, attempts, scoring, selection, report |
| Coder | 10 | one file each | The complete file, nothing else |
| Tester | 5 | no | T1 contrast, T2 syntax and tokens, T3 structure and a11y, T4 clean output, T5 motion budget |
| Reviewer | 5 | no | R1 slop, R2 fit to brief and palette, R3 Liquid Glass nav, R4 copy and voice, R5 responsive |

Output format: a coder returns file contents only. Testers and reviewers return `{"findings":[{"gate","file","msg"}]}`, with `[]` when clean.

## 3. File ownership

| Coder | File | Job |
|---|---|---|
| C1 | index.html | Semantic structure, real content, section order |
| C2 | tokens.css | Tokens from the direction (OKLCH, light and dark), no default navy |
| C3 | base.css | Reset, type scale, grid, focus, buttons with all states |
| C4 | nav.css | Liquid Glass pill nav, invisible at top, visible on scroll |
| C5 | nav.js | Refraction and scroll state (`data-scrolled`) |
| C6 | hero.css | Hero composition with one signature move |
| C7 | sections.css | Sections and responsive layout |
| C8 | forms.css | Forms, errors, empty states |
| C9 | motion.css | Scroll reveal, stagger, exits, shimmer, reduced motion |
| C10 | main.js | Menus, reveal fallback, validation, no globals |

Coders run in parallel and never touch another coder's file. Class and token names come from the direction card's contract, not from another coder's output.

## 4. Direction card (locked per attempt)

Five lines, sent verbatim to every coder: direction name, type pair, palette hue and accent logic, layout and hero archetype, nav preset. The list of class names and tokens is part of the card.

Directions tried in order: Warm paper, Civic clear, Local craft, Brutalist signal, Soft organic. None uses a blue-navy or violet background. A direction with a background hue in the 225 to 290 range is rejected by gate R2 unless the brief explicitly asks for it.

## 5. Hard rules

- **No default navy.** Background tokens may not sit in the 225 to 290 hue range unless the brief names it. This is enforced by gate R2.
- **Liquid Glass nav is required.** Rounded pill (`border-radius` 9999px or equivalent), `backdrop-filter`, scroll state, fallback under `prefers-reduced-transparency` and `forced-colors`. Enforced by gate R3.
- **Motion budget.** At least 3 `@keyframes`, at least 4 animated declarations, a reduced-motion rule, and no layout-property transitions. Enforced by gate T5.
- **Identity on the first screen.** At least one strong accent or two hue families visible above the fold. Judged by R1.
- **Glass only on the nav and at most one floating layer.** Judged by R1.
- **One contract.** Every `var(--x)` and class used in the HTML must be defined. Enforced by gate T2.
- **Clean output.** No lorem, TODO, console, debug or section-label comments. Enforced by gate T4.

## 6. Gates (deterministic, run before any model)

- T2 syntax: `node --check` on every JS file, brace balance on every CSS file, undefined tokens.
- T3 structure: `lang`, viewport meta, `alt` on images, exactly one `h1`, no `div` acting as a button.
- T4 clean output: forbidden patterns.
- T5 motion budget: keyframes, animated declarations, reduced-motion rule, layout transitions.
- R2 palette: banned hue range on background tokens.
- R3 Liquid Glass nav: backdrop filter, pill radius, transparency fallback, scroll state.

Gates decide pass or fail. Reviewers add judgment on top of gates. A build that passes every gate but reads as generic still gets flagged by R1.

## 6bis. Integration gate (added after a build shipped with no Liquid Glass)

A v5.6 build first passed without a working Liquid Glass nav: the nav styles existed in `nav.css` but nothing in `index.html` used them, so the effect never reached the page. Gate `T3 integration` now requires:
- every CSS file linked from `index.html`, and every JS file loaded from it;
- an element with class `site-header` and one with class `nav` in the HTML;
- `nav.js` targeting `.site-header` or `.nav`, and applying the Liquid Glass effect.

A file that exists but is not wired in fails the build.

## 7. Model boundary

`runAgent(role, prompt)` is the only place a model is called. It runs the command in `AGENT_CMD`, passing the role on argv and the prompt on stdin, and reads the answer on stdout. Without `AGENT_CMD`, it runs offline: coders produce empty files and the gates report them. This proves the pipeline works before a model is connected.

## 8. Limits

- At most 10 coders in parallel per attempt, and 10 testers and reviewers per judge round.
- At most 3 attempts and 2 repairs per attempt.
- A coder that returns anything other than a file is treated as failed.

## 9. Files

- `orchestrator.mjs`: runnable orchestrator with all gates. Usage: `AGENT_CMD=/path/to/agent node orchestrator.mjs ./site "brief"`.
- `v5.6-LiquidGlass-agent-skill.md`: this file.
- `reference-site/`: a small site that passes every gate, with a working Liquid Glass nav. Use it as the wiring example for coders.
